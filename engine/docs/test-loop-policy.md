# 검증 루프 정책 — 게이트는 줄이지 않는다 (2026-08-26 동결)

사장님 결정. 배경: 어제 밤 832건 14분 47초 → 오늘 아침 926건 23분 42초.
하루에 +94건이면 일주일 뒤 스위트는 한 시간이고, **그때부터는 아무도 전체를
안 돌린다.** 렉의 정체는 기계가 느려지는 게 아니라 사람이 검증을 건너뛰기
시작하는 것이다(계획서 §5 ②).

이건 남의 문제가 아니다 — 우리가 파는 것이 "장기 프로젝트를 끝까지 끌고 가는
AI"이므로, 이 저장소에서 재는 이 숫자가 그대로 제품의 계기판이다.

---

## 1. 두 줄로 나눈다

| | 명령 | 시간(2026-08-26 실측) | 언제 |
|---|---|---|---|
| **상시 게이트** | `pytest -n 4` | **8분 18초** (982건) | 커밋 전, 판정 전, 하루 마무리 |
| 안쪽 반복 | `pytest -n 4 -m "not slow"` | **5분 6초** (968건) | 고치는 중 여러 번 |

정직하게: 아낀 시간은 **3분 12초(38%)** 이지 몇 배가 아니다. 느린 14건을 빼도
남는 968건이 5분을 먹는다 — 즉 이 스위트의 무게는 몇 개의 괴물이 아니라
**전체 부피**에도 있다. 부분집합은 그 사실을 가리지 않는다.

`-m "not slow"`는 **기본값이 아니다.** `pyproject.toml`의 `addopts`에 넣지
않았고, 넣지 못하게 막는 테스트가 있다(`tests/test_slow_registry.py`의
`test_default_run_does_not_deselect_slow_tests`). 빠른 부분집합은 편의이고
게이트가 아니다.

## 2. "느리다"는 잰 값이다

`data/slow_tests.json`에 nodeid와 **측정된 초**가 들어간다. 생성은
`tools/slow_tests.py --from-log <pytest --durations 로그>`뿐이고, 손으로 추가
하지 않는다 — 사람이 "느릴 것 같다"고 붙이기 시작하면 부분집합이 측정이 아니라
인상이 된다. 표식은 `conftest.py`가 수집 시점에 자동으로 붙인다(데코레이터를
테스트 파일에 흩뿌리지 않는다).

문턱은 **20초**다. 한 번 도는 데 20초를 넘는 테스트 하나면 안쪽 반복이 그
테스트에 끌려간다. 이 숫자는 개발 도구의 정책값이고 **판정 문턱이 아니다**
(심판 문턱과 달리 결과를 보고 조정해도 무엇도 왜곡하지 않는다).

## 3. 병렬화에서 배운 것

| 방식 | 시간 |
|---|---|
| 직렬 | 23분 42초 |
| `-n 4` (기본 dist=load) | **11분 57초** (1차 · §3 변동폭 참고) |
| `-n 4 --dist worksteal` | 13분 5초 (더 느림 — 기각) |

전체 CPU 시간이 약 24분이므로 4워커의 이론 바닥은 6분인데 12분이 나온다.
일이 고르게 안 나뉘기 때문이고, 그 원인은 **소수의 긴 테스트**다. 그래서
병렬화만으로는 더 못 줄인다.

### 측정 변동폭을 정직하게 남긴다

같은 날 같은 기계에서 두 번 잰 값이 이만큼 흔들린다:

| 테스트 | 1차(10:39) | 2차(11:51) |
|---|---|---|
| `test_mine.py::test_known_positive_qualifies` | 184.1초 | 109.3초 |
| `test_mission6.py::...audit[K]` | 159.5초 | 143.3초 |
| 전체 스위트 | 11분 57초(925건) | **8분 18초(982건)** |

테스트가 57건 늘었는데 시간은 줄었다. 즉 이 숫자들은 **±30% 쯤 흔들린다**고
보고 읽어야 하고, 한 번의 측정으로 "빨라졌다"고 말하면 안 된다. 문턱 20초
근처의 테스트는 주행마다 등록부에 들락날락한다 — 그래서 등록부는 **그때 그
주행의 스냅샷**이고, 갱신 절차(§5)가 있는 것이다.

## 4. 안 하는 것

- 상시 게이트에서 `slow`를 빼는 것. 그건 "전체를 안 돌리게 되는" 위험을
  제도화하는 것이다.
- 느린 테스트를 **삭제**하는 것. 상위 4건은 전부 연구 레인(mission6·loop·mine)
  이고 주력은 아니지만, 그 결과가 현재 설계의 근거다(무엇이 안 되는지를
  증명한 기록). 느리다는 이유로 증거를 지우지 않는다.
- 등록부를 손으로 고치는 것.

## 5. 갱신 절차

전체 주행을 `--durations=0`으로 돌린 뒤:

```
python -X utf8 tools/slow_tests.py --from-log data/suite_gate_YYYYMMDD.log
```

(2026-08-26 최초 등록은 `--durations=20` 로그라 20건에서 잘려 있었다. 같은 날
`--durations=0` 완전 주행으로 다시 만들어 **14건**이 됐다 — 잘린 목록이 실제보다
많아 보였던 게 아니라, 1차 주행에서 20초를 넘겼던 테스트 여럿이 2차에서는
그 아래로 내려갔다. §3의 변동폭 그대로다.)

## 6. 측정 전에 기계가 한가한지 본다 (2026-08-26 18:5x, 사고 기록)

18:47에 스위트가 **31분 동안 6%**에서 기어가고 있었다. 나는 그 직전 커밋
(`fce5ece`)에 *"오늘 만든 legal 통제 때문에 8분 28초 → 14분 55초가 됐다"* 고
적었다. **확인 없이 단정한 것이었고, 틀렸다.**

실제로 본 것:

| | |
|---|---|
| CPU 사용률 | **100%** (논리 코어 4) |
| 최상위 소비자 | **Claude 앱 프로세스 둘** (CPU 시간 2901초·2797초) |
| 파이썬 워커 | 상위 8위 안에도 없음 |

같은 파일(`test_icon_lane.py`)이 12시 2.82초 → 18:47 5.06초(1.8배)였다.
기계가 도구에게 먹히고 있었고, **15시 이후의 게이트 시간은 전부 오염된 측정
이다.**

### 그래서 무엇이 참인가

- **참**: `test_golden_bench` 144초 → 52초(같은 기계 상태에서 앞뒤로 잰 값).
- **모름**: 전체 스위트가 실제로 느려졌는지, 느려졌다면 얼마나.
- `legal_n` 수정 자체는 유효하다 — 관문을 헐겁게 만들지 않고(줄여 부르면
  최소 표본 미달로 강등) 테스트만 빨라진다.

### 규칙 추가 (동결)

**시간을 재기 전에 기계 부하를 확인하고, 그 값을 측정과 함께 남긴다.**
경합 상태에서 잰 값으로 "빨라졌다/느려졌다"를 말하지 않는다. 오늘 §3에 적어둔
±30% 변동폭도 이 원인을 포함하고 있었을 수 있다.

이 사고의 교훈은 도구가 아니라 **추론**에 있다: 느려진 것을 보고 **가장 최근에
내가 만든 것**을 원인으로 지목했다. 그게 제일 그럴듯해 보였기 때문이지, 재봤기
때문이 아니다.
