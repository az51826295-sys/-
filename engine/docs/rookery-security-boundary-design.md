# 고객 저장소 보안 경계 — 설계 초안 (2026-08-22, 미동결 · 사장님 결정 대기)

상품화 메모(docs/rookery-monetization-memo.md)의 병목 3. 지금 제도는
"우리 노트북의 남의 오픈소스 코드"용으로 설계됐다. 돈을 받고 **고객의
저장소·비밀·의존성**을 받는 순간 경계가 제품 문제가 된다. 이 문서는 현재
경계를 정직하게 적고, 파일럿 전에 필요한 최소 경계와 그 뒤를 나눈다.

## 1. 현재 경계 (사실)

| 층 | 있음 | 없음 |
|---|---|---|
| 명령 | 허용목록(python·pytest·git)·git 하위명령·셸 메타문자·배포/결제 토큰 차단, 거부 로그 | **네트워크 차단 없음** — pytest·python 서브프로세스는 바깥에 나갈 수 있다 |
| 파일 | 작업공간 밖 경로 거부(`resolve`), `.git` 금지, 비밀 경로 패턴(.env·.ssh·credentials…) 차단 | 서브프로세스(테스트 실행)는 **OS 전체**를 본다 — 컨테인먼트는 엔진 도구에만 걸린다 |
| 프로세스 | 과제당 워크트리, 12스텝, 예산 원장 | 컨테이너·사용자 분리·리소스 제한 없음 |
| 데이터 | 원장 저장소별, 채택 브랜치 로컬 | 테넌트(고객) 분리 없음, 원장·로그에 고객 코드 조각(응답 원문)이 남음 |
| 모델 | 프롬프트에 장부 불주입, 단가 운영자 값 | 고객 코드가 모델 API로 나간다(불가피) — 고객 동의 문구 필요 |

## 2. 파일럿(무료, 오픈소스 1곳) 전 최소 경계 — "지금 제도 + 3개"

1. **서브프로세스 실행 경계**: 테스트 실행을 컨테이너(또는 최소 별도 OS
   사용자 + 네트워크 차단 namespace)에서. Windows 노트북에선 WSL2+Docker가
   현실적 → 사실상 Linux 서버 배포(deploy/)와 같이 간다. 오픈소스 파일럿은
   코드가 공개라 이 층 없이도 **위험이 우리 기계에만** 있다 — 파일럿은 지금
   경계로 가능, 유료 전엔 필수.
2. **비밀 유입 차단**: 고객 저장소 클론 시 `.env`·키 파일을 받지 않게
   sparse/필터, 비밀 패턴 스캔을 워크트리 생성 시에도(지금은 명령 인자만).
3. **응답 원문 보존 정책**: `agent_response` 이벤트(모델 응답 원문 3000자)는
   부검용이지만 고객 코드 조각을 담는다 → 테넌트별 원장 + 보존 기간(예: 30일)
   + 고객 요청 시 삭제 절차.

## 3. 유료 전 경계

- 테넌트 분리: `<data>/<tenant>/<tag>/<repo>/` + 키·예산·정지 전부 테넌트별.
- 감사 로그 공개: 고객이 자기 저장소의 명령·거부·지출·채택 이벤트를 읽을 수
  있는 내보내기(출처 계약 헤더 포함).
- 모델 전송 고지·동의: 어떤 코드가 어느 모델로 가는지(저장소·파일 단위).
- 푸시 경로: 고객이 원하면 고객 포크에만 푸시(지금은 전부 로컬).

## 4. 하지 않을 것

- "샌드박스 없이도 안전하다"고 말하기. 지금 경계는 우리 기계 기준이다.
- 고객 비밀을 모델 컨텍스트에 넣는 어떤 편의도.
