## 2. 엔진 구성 — 살아 있는 길과 옛날 짐

**살아 있는 길** (사용자 한 마디가 지나가는 자리)
`/ask` 대화 → 일상 서비스(검색·그림·위임 판단) → 직원 접수(`runChatTurn`) → 업무 → **실행 엔진(웹 프로세스 안)** →
기술(appBuild·meshAssets·gameAssets·artBible) → 공급자(라우터: DeepSeek 먼저 / OpenAI · 그림 · Meshy · 심판 서비스 · Tavily) →
결과물·파일(Supabase) → 대화에 붙임 → 유니티 창(가져오기·짓기·검사) → `/api/unity/checks` → 대화.
서비스는 셋: 웹(Railway), 심판(Railway, Python), DB+저장소(Supabase 작은 인스턴스).

**옛날 짐** (AI 직원 SaaS 시절, /ask 가 안 쓰는 것) — 전체 21,800줄 중 약 5,000줄
- playbooks(737) · policies(664+257) · collaboration(412) · genesis(genome/predict) · recurring · onboarding · memory.
- 실행 엔진의 `selection`·`citations`·직원 정의 953줄 중 상당수.
- 다만 **marketResearch(420)·leadResearch(949)** 는 버릴 게 아니다 — 사장님이 말한 "분석" 종류의 직원이 이미 있는 셈이다.
  종류 등록표(`work/kinds.ts`)의 analysis 자리에 이 둘을 붙이면 된다.

**구조가 오늘 실제로 낸 사고**
1. **실행이 웹 프로세스 안에서 돈다.** 배포하면 도는 일이 죽고(오늘 두 번), DB 가 멈추면 같이 멈춘다. 죽은 줄도 40분 뒤에야 안다.
   → 실행을 **워커 서비스**로 뺀다(Railway 서비스 하나 더). 엔진은 이미 `db` 를 받는 스케줄러 경로가 있어 오늘 그 길로 로컬에서 돌렸다.
   웹은 접수만 하고, 워커가 대기열을 꺼내 돈다. 배포가 일을 안 죽인다.
2. **DB 가 작고 행이 뚱뚱했다.** 그림 base64 가 대화 행에 들어가 6초 폴링에 25분씩 두 번 멈췄다(오늘 고침). 원칙: **큰 것은 행에 넣지 않는다.**
   저장소로, 행엔 경로만. 남은 위험은 결과물 행의 파일 본문(코드 100KB×판). 다음엔 그것도 파일로.
3. **비용을 모르는 라우팅.** 오늘 DeepSeek V4 로 바꿨다(판단 자리도 pro 먼저, 실패 시 gpt-5). 다음 Dev 판부터 값·품질을 잰다.
4. **자(검사)가 사장님 PC 의 유니티다.** 사장님이 안 켜면 아무도 못 잰다. 당장은 그대로(깨끗한 기계 목표는 폐기됨), 워커가 생기면
   워커 옆에 유니티 헤드리스를 붙일 수 있다 — 그때 "사람 손 0회" 가 된다.

**정리 순서 (제안)**
1. 워커 서비스 (반나절) — 오늘 잃은 시간의 절반이 여기서 났다.
2. 장부 완성 + 한도 (반나절).
3. 옛날 짐 접기: 지우지 않고 `src/lib/_legacy/` 로 옮기고 import 를 끊는다. 컴파일에서 빠진다 (두 시간).
4. 결과물의 코드 본문을 파일로 (한 시간).
5. 그 다음에 UI B (이틀).
