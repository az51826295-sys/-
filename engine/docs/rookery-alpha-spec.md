## 0. 결과 표현 규약 (과잉 일반화 금지)

이 사양이 인용하는 연구 결과는 **아래 범위로만** 쓴다.

- **기억에 대해**: "기억이 실패했다"가 아니라 —
  > 현재 Haiku 4.5와 이 과제군에서, **프롬프트에 누적 이력·점수·
  > 서명을 추가하는 방식**의 기억은 독립적 성능 기여를 입증하지
  > 못했다.

  레지스트리·구조화 상태·외부 DB·검색 기반 기억은 **검정된 바
  없다**. Alpha는 상태 레지스트리를 당연히 쓰며, 그것은 위
  결과와 무관하다.
- **회귀 가드에 대해**: 회귀형에서만 작동이 확인됐고 불완전형은
  정보 경계 (§8.5).
- **다양성에 대해**: 온도·패딩·서명 이력으로는 실코드 원인 고착이
  안 열렸다. 구조적 단계 분리(§6.11)만 유일하게 열었다.

## 1. 제품 경계 — 무엇을 자동화하는가

검증의 비대칭(§8.5)이 경계를 정한다.

- 기존 동작 파손 = 기존 테스트로 **잡기 쉬움**
- 새 요구사항 미구현 = 기존 테스트로 **잡기 어려움** (원리적)

따라서 **명세가 명확하고 판정 가능한 작업만 자동화한다.**

- **1순위 (Alpha 착수)**: 코드 회귀 수정, 테스트 보강, 문서 포맷,
  데이터 변환 — 판정 기준이 기계적인 일.
- **후순위**: 창의적 완성도·숨은 요구사항이 많은 일. 명세화 전에는
  자동 채택 금지.

## 2. Validator Auditor (Validator 위의 계층)

발견된 계측기 오류 3건은 단순 실행 오류가 아니라 **"잘못된 숫자를
그럴듯한 결과로 만드는 버그"**였다. 따라서 판정기 위에 감사 계층을
둔다.

```
작업 결과 → Validator 판정 → Auditor 역검증
          → 일치하면 채택 / 불일치하면 자동 정지
```

**Auditor는 같은 계산을 반복하지 않는다. 다른 불변식을 본다.**
동결 불변식 5종:

1. 부모 커밋에서 실패하고 수정본에서 통과해야 한다
2. 정답 패치조차 실패하면 그 테스트는 무효다
3. 사용된 과제는 신규 후보로 다시 등장하면 안 된다
4. 결과가 전부 0이면 경로·파싱 오류를 의심하고 검사한다
5. 성능이 갑자기 완벽해지면 천장·누출을 검사한다

근거 사례: ①은 §8.3 selfcheck가 잡은 fail→fail 거짓 양성, ③은
§9.2의 stale 소진 목록, ④는 §9.1의 역슬래시 노드 ID(정답과 오답이
같은 0/9였다), ⑤는 §6.5의 Haiku 원샷 천장.

## 3. 위험도 기반 후보 예산 (고정 다수 후보 아님)

측정 단가(§6.18: 351호출 ≈ $2.5)로 API 3만 원 ≈ **월 3,000호출 =
하루 약 100호출**. 무작정 다수 후보는 예산이 감당 못 하고, 후보 1개
고정은 첫 가설 고착(§6.11의 오파일 고착)을 부른다.

| 작업 난이도 | 후보 수 |
|---|---|
| 쉬움 (명세 명확·국소) | 1 |
| 보통 | 2 |
| 불확실성 높음 | 3 |

3개 모두 실패하면 **중단하고 실패로 기록** (무한 재시도 금지).

## 4. 실패 로그 → 과제 변환 게이트

실패 로그를 그대로 과제로 삼으면 계측기 오류·일시적 API 오류까지
학습 대상이 된다. 아래를 **전부** 통과해야 과제가 된다.

```
실패 발생 → 재현 가능성 확인 → 평가기 정상 여부 확인
        → 기존 과제와 중복 확인 → 해결 가능성·가치 평가
        → 신규 과제로 등록
```

## 5. 자동화 범위와 차단

- 격리 브랜치 **내부**의 수정·실험·채택·롤백은 사람 승인 없이 자동
- 검증된 결과는 **자동 PR 생성**
- **운영 브랜치 자동 머지는 Alpha에서 비활성화**
- **차단**: 위험 명령, 비밀정보 접근, 외부 배포, 결제·권한 변경

## 6. 예산

- 월 총 6만 원 이내 (서버 1~2만 + API 기본 3만)
- **월 4만5천 원 도달 시 신규 작업 자동 중지**
- 사용량·예상 잔액 일일 보고

## 7. 합격 기준

### 필수 (하나라도 미달이면 불합격)

1. 7일 연속 무인 실행
2. 서버 재시작 후 자동 복구
3. 완료된 작업 재실행 **0건**
4. 예산 초과 **0건**
5. 격리 밖 파일 수정 **0건**
6. 위험 명령 실행 **0건**
7. 판정기 불일치 시 자동 정지 **100%**
8. 일일 보고 누락 **0건**

### 성능

- 검증 가능한 실제 작업 **최소 20건**
- 그중 자동 완전 처리 **5건 이상**
- 회귀를 만든 패치 자동 채택 **0건**
- 실패 이유 분류 가능률 **90% 이상**

**"스스로 진화"는 합격 조건에서 제외하고 관찰 지표로만 둔다.**

## 8. 구현 순서 (동결)

1. Resume Runner
2. 비용 제한
3. 작업 격리
4. Validator Auditor
5. 실패 로그 → 재현 과제 변환
6. 위험도 기반 후보 수 조절
7. 일일 보고
8. 서버 배포
9. 7일 무인 시험

기억·자가진화·Sonnet 7E 등 연구는 **Alpha가 실제로 돌아간 뒤**
보조 레인으로.

## 9. 기착수 자산

- `genesis/rookery/engine/store.py` — Task/Run 레지스트리 (SQLite,
  리스 기반 크래시 복구). 순서 1의 본체.
- `genesis/rookery/runlog.py`·`runner.py` — 실험용 resume, 하드 킬
  재개 검증 완료 (§10.1). 설계 참조.
- `genesis/rookery/regression_guard.py` — 회귀 가드 5규칙 (§10.2).
  순서 4의 Validator 측 절반.
- `genesis/rookery/spent.py` — 자동 소진 레지스트리. Auditor
  불변식 ③의 구현체.
- `genesis/preflight.py` — API 파라미터·키·게이트 사전 검증.
