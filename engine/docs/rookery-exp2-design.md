# Rookery 실험 2 설계 — 상호작용 버그 코퍼스 v2 (사전 등록)

작성: 2026-08-02. 상태: 초안 — 난이도 보정 파일럿 후 동결. 근거:
실험 1의 R4 발동 + 사용자 방향 결정 (2026-08-02: ① 다중 함수 모듈 +
상호작용 버그 2개; 긴 사양형은 독해 측정, 실제 OSS는 교란 과다).

핵심 질문:

> 단일 호출로 자주 불완전한 패치를 만드는 상호작용형 코드 과제에서,
> 동일 예산의 다양한 후보 생성·기계적 중복 제거·숨김 검증·
> champion–challenger 롤백 구조가 순차 단일 에이전트보다 완전
> 해결률과 실패 후 회복률을 높이는가?

## 1. 과제 구조 (생성 규칙)

- 과제당 Python 모듈 3~5함수, 80~200줄. 공유 상태(카탈로그·캐시·
  원장·계좌)와 작업 순서 의존성 필수.
- **버그 정확히 2개, 상호작용형**: 독립 오타 금지. "버그 1만 고친
  패치가 숨김 상호작용 테스트를 깨뜨릴 수 있는" 구조. 유형 예:
  캐시 갱신 vs 입력 정규화, 할인 vs 반올림 순서, 재고 차감 vs 취소
  복구, 경계 처리 vs 상태 누적, 부분 실패 vs 원자성.
- 테스트: 공개 4~6 (한쪽 증상만 노출) / 숨김 8~12 (부분 수정·
  하드코딩·과잉 조건·회귀·두 버그 조합·상태 누적 실패 포착) —
  숨김에 회귀 3~5·상호작용 2~4 포함.
- 자체 검증 의무: 참조 수정본(fixed_code, 모델에 미노출)이 전 테스트
  통과, 버그본이 공개 ≥1·숨김 ≥1 실패, 회귀 테스트는 버그본도 통과
  (기존 정상 동작). 대표 과제는 "버그 1만 수정" 부분 패치가 숨김
  상호작용 테스트에 실패함을 기계 검증.

## 2. 난이도 보정 파일럿 (동결 전, 6문제 × 3반복 단일 호출)

목표 분포 (첫 호출 기준):
- 완전 해결(숨김 전부): 30~50%
- 공개만 통과 (회귀 생산): 20~40%
- 완전 실패 (공개도 실패): 20~30%
- 반복 3회 간 구조적으로 다른 유효 패치 존재: 과제 절반 이상

범위 밖이면 **같은 문제의 테스트를 몰래 강화하지 않고**, 생성 규칙을
고쳐 새 문제로 교체한다 (선택 편향 방지). 파일럿 문제는 본실험에
재사용하지 않는다 — 본실험은 독립된 18~24문제 (중간 8 / 높음 8 /
잠복·상호작용 4~8 계층).

### 보정 파일럿 1차 결과 (2026-08-02) — 목표 미달, 규칙 수정 필요

완전 해결 **100%** (18/18), 공개만 0%, 실패 0%. 구조적 상이 패치
4/6 (통과). 진단: ① 모듈이 40~60줄로 설계 하한(80~200) 미달, ②
버그가 코드만 읽어도 보이는 국소형 (연산자·누락 호출 — Haiku가 코드
대조로 즉시 발견), ③ **함수별 사양이 정답 명세를 그대로 서술**해서
"사양 vs 코드 diff" 문제로 환원됨.

규칙 수정안 (v2.1, 새 문제로 재작성):
1. 모듈 120~250줄·함수 5~7개, 버그 지점과 증상 발현 지점을 다른
   함수로 분리 (간접 상호작용).
2. 사양은 **모듈 수준 목적 + 입출력 예시**만 제공 — 함수별 계약을
   정답 수준으로 서술하지 않는다.
3. 버그는 국소적으로 자연스러워 보이는 형태 (올바른 코드처럼 보이는
   순서·불변식 위반)로 한정, 연산자 오타류 금지.
4. 그럴듯한 수정 지점이 2개 이상 존재하도록 미끼 경로 포함.
목표 분포는 동일 유지. 재보정은 새 6문제로.

### v2.1 대표 과제 보정 결과 (2026-08-02) — 전환 기준 충족

대표 과제 storefront (4섹션 ~120줄, 상호작용 버그 2개: 정산이 표시
라운딩을 재사용 + 취소가 리포트 캐시 미무효화, **기계 검증된 미끼
2종** — 정산만 수정 / 표시·정산 통일 — 이 공개 100% 통과·서로 다른
숨김 프로필로 실패):

- Haiku 10회 단일 호출: **완전 해결 8 / 공개만 0 / 실패 2** (목표
  3~6 / 2~5 / 1~3). 오답 패치 다양성 측정 불가 (공개만 통과 표본 0).
- 사전 등록된 전환 기준 발동: "미끼 패치가 공개 테스트를 통과하도록
  만들었는데도 원샷 70% 이상이면 실제 저장소 v3로 넘어간다" — 80%로
  충족. **자기완결 합성 과제는 이 모델의 원샷 능력 아래에 있다**가
  세 번의 보정(v1 100%, v2 100%, v2.1 80%)에 걸친 일관 결론.
- v3 (실제 저장소, 외적 타당성 단계)로 이행. 통제 설계 — 저장소
  탐색·문서 품질 교란을 최소화하는 고정 소형 저장소 + 재현 커밋 —
  는 별도 등록 문서에서.

## 3. 비교군과 예산 공정성 (실험 1에서 강화)

A(순차 단일)·B(제도형)는 실험 1과 동일 구조. 동일 통제 항목 확장:
총 호출 수, **총 입출력 토큰(사후 보고·상한)**, **테스트 실행 횟수
(양군 동일 상한)**, 숨김 테스트 비노출(선택은 공개만), 비용.

## 4. 가설 (본실험 등록 시 동결)

- R5: B 완전 해결률(숨김 전부) ≥ A + 15%p.
- R6: B 회귀율 ≤ A − 10%p (다양한 후보 중 회귀 없는 것을 선택).
- R7: B 실패 후 회복률 > A + 15%p.
- R8 (정직 조항): 동률이면 난이도 경계를 더 탐색하고, A 우위면 제도
  오버헤드가 손해라고 기록한다.

## 5. 절차

1. 파일럿 코퍼스 6문제 작성 + 자체 검증 (참조 수정·부분 수정 포함)
2. 난이도 보정 파일럿 (6×3 단일 호출, ~$0.1) → 분포 확인
3. 규칙 보정 → 본 코퍼스 18~24문제 → 등록 동결 → 본실험 → 판정
4. v3 (실제 OSS 이슈)는 v2에서 제도 효과가 확인/기각된 뒤 외적
   타당성 단계로.
