## 2. 팔 수 있는 형태 — 세 가지, 정직한 가격표

### A. "우리 저장소 버그 잡아주는 신입" (수리 구독)
고객 저장소를 붙이고 매일 이슈를 스캔·재현·수리해 **PR 초안**을 올려준다
(머지는 고객). 
- 원가: API는 고유 해결당 $5.33(위 표), **사람 시간 미측정** — 원가 기반 가격은 폐기(§6 Q2). 이전 초안의 "$2.15 + 실패분 $4~6"은 이중 계산이라 정정.
- 제약: 현재 해결률 20~30%(오픈소스 실 이슈 기준), 사람 검토 필수(G-c 0.8), 고객 저장소 격리·비밀 유지는 **미구축**(엔진은 로컬 워크트리 전제).
- 가격 감: 해결 건당 $20~50 또는 월 정액 + 건당 — 원가 대비 여유는 있지만 "해결 1건"의 가치를 고객이 인정해야 함.
- 필요한 것: 고객 저장소 온보딩(클론·테스트 실행 환경), 멀티테넌트 원장, 보안 경계, 머지율 실적(G-b).

### B. "검증 제도 자체" (오픈 제도 + 운영 서비스)
엔진보다 **제도**(격리·예산·감사·위생·Goodhart)를 상품으로: 다른 회사의
AI 에이전트 산출물을 우리 게이트로 검증·감사해 주는 서비스, 또는 제도를
오픈소스로 풀고 운영·감사 대행을 판다.
- 강점: 모델이 좋아져도 남는 가치(모델은 남의 것, 제도는 우리 것). 오늘
  하루의 부검 사슬(계측 결함 12건을 기록으로 잡아 수리)이 데모 그 자체.
- 약점: 시장이 "에이전트 감사"를 돈 주고 사는지 **미측정**. 판매 대상이
  개발팀장급이라 영업 비용이 큼.

### C. "AI 직원 회사" (ai-workforce 제품의 본래 그림)
Rookery SaaS(ai-workforce)에 루키를 첫 직원으로 입사시키는 것: 대화로
일을 시키고(채팅 쓰기 경로 v1), 일한 기록이 원장·PR 큐로 남는 "고용"
경험.
- 강점: 제품 서사가 이미 있음(직원·온보딩·플레이북). 루키 채팅(성실한
  신입, 숫자로 말함)은 실물.
- 약점: 현재 루키가 잘하는 일은 "재현 테스트가 있는 코드 수정"뿐. 일반
  업무 직원은 아님. 과대 포장 위험 — 제도 원칙(안 한 걸 했다고 안 함)과
  충돌하지 않게 범위를 좁혀야 함.

그리고 §4의 게이트 두 개(머지 1건, $12 재측정)는 결정을 무기한 미루거나 판정
불가를 낳는다는 지적 → **대체 게이트 3개(전부 $0, 이번 주)**:

(i) **재현 단계 성공률 — 재집계 + 무효 원인 분류 완료(08-22 밤, $0)**. 첫 보고는
수율·해결률을 섞어 "다른 질문에 답"했다는 지적이 맞았고, 재집계 중 **더 큰 것**이
나왔다: 무효 86%의 원인은 유도 품질이 아니라 **환경**이다
(docs/live-intake-filter.md 분류 결과).
- **오염된 블렌디드 값은 인용하지 않는다**: v1 24.6%·v2 9.4%·합계 15.8%는 src
  레이아웃 저장소(marshmallow·dateutil·sortedcontainers)가 인테이크 워크트리에서
  import되지 않아 전량 폐기된 것에 오염됐다.
- **순수 재현율 ≈ 30% (삼각측량; 오라클 확정 불가, 아래)**. 세 컷이 수렴한다:
  - verify 정의(HEAD에서 FAILED=accepted, 느슨): env 수리 후 v1 57.4%·v2 71.8% —
    **상한, 무관 실패 포함**.
  - **AssertionError 실패만**(라이브러리가 틀린 값 산출 = 행동 재현, 가장 타이트한
    기계 대리): v1 **17/61=27.9%**, v2 **26/85=30.6%**.
  - root 저장소만(env 무관): v1 40.5%·v2 31.6% (단 이것도 느슨한 verify 정의).
  두 독립 대리(AssertionError ~28~31%, root-only ~31~40%)가 ~30%로 수렴 — **그러나
  이 ~30%는 오염돼 있다**(아래).
- **왜 "확정"이 아니라 "삼각측량"인가**: fix-commit 오라클(수정 후 통과?)은
  **열린 이슈엔 존재하지 않는다**(고칠 커밋이 아직 없음). 유일한 진짜 오라클은

  단언하면 위양성, 예외로 드러나는 버그면 위음성). 그래서 단일 확정값이 아니라
  ~30% 중심 추정. **정정(층화 표본 측정, 2026-08-22)**: AssertionError는 기능
  요청도 낸다(assert 없는 API 존재→False) — 표본 10건 중 진짜 버그 재현은 **3건**,
  나머지는 기능요청·깨진 테스트·데이터파일 부재. 순수 **버그** 재현율은 ~30%가
  아니라 **10~25% 미확정**(기능 요청을 걸러낸 뒤의 수가 진짜 공급). 배수는 분모
  병기: v2 7.6배(61/85 vs 8/85)·v1 2.3배(35/61 vs 15/61)·합계 4.2배(96/146 vs
  23/146). 오염률이 스트라텀별로 80% vs 60%로 달라 apples-to-apples는 미확증.
- **기능요청 필터 후 재집계 — 단일값 철회(146건 전수, 사후, $0)**: **분류 규칙을
  숫자 보기 전에 등록하지 않았다(사후값)**. 기능요청 23/146=16%를 뺀 버그 후보 123에

  게이트가 4배로 어긋난다(예외-단어 24% vs 심볼 ~100%). 결과는 사후 게이트 선택에
  민감: **8.9%(예외-단어)·29.3%(값단언만)·40.7%(심볼)·66.7%(전부)** — 방어 가능한
  단일값 없음. 앞의 "29~38%/29.3% 가장 방어 가능"은 **철회**. 사전 등록된 유일 측정은
  10건 표본 수동(3/10 진짜, n=10). 진짜 단일값은 사전 등록 규칙을 새 데이터에 돌리거나
  fix 오라클(부재)이라야 나온다. "수리하면 오른다"는 예측이라 영업 문장 금지, 내부
  로드맵만(상한 19/123=15.4%p). **확정값은 기능요청 16% 하나** — 이건 상품 문구.
- **부수 발견(계측)**: verify의 "FAILED=accepted" 게이트는 **root 저장소에서도**

  무관하게 견고하다 — 고유 기준 13/5 = **2.6배**, 이벤트 기준 23/8 = **2.9배**
  (단위를 섞은 "15.8%×38%"식은 폐기; 두 단위 중 하나로만 센다).
