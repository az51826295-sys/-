## 사장님 요청 — **원문**

> **"점프를 더 쫀득하게"**

이 위의 한 줄이 요청이다. 아래는 **사장님이 따로 주신 해석**이며, 원문과 섞지 않는다
(개정판 2 ④: 원문 그대로 남긴다 · 사장님 09-22: *"해석은 따로 적는 게 맞습니다"*).

### 사장님 해석 (2번 칸을 판정할 기준)

> *"쫀득하다" 를 게임 손맛으로 풀면 대체로 **둥둥 뜨지 않고, 누른 대로 반응하고,
> 꼭대기에서 살짝 버티다 탁 떨어지는** 느낌입니다.*

| | 해석 항목 | 사장님 말 |
|---|---|---|
| ㉠ | **곡선 모양** | 빠르게 솟고, 꼭대기에서 아주 잠깐 머물고, 내려올 땐 올라갈 때보다 빠르게 떨어진다. **쫀득함의 핵심은 대부분 여기** |
| ㉡ | **누르는 길이** | 짧게 누르면 낮게, 길게 누르면 높게. 점프가 내 손을 따라온다는 느낌 |
| ㉢ | **관대함** | 발판 끝에서 살짝 늦게 눌러도 뛰어지고, 착지 직전에 미리 눌러 둔 점프도 먹힌다 |
| ㉣ | **보이는 탄력** | 뛸 때 살짝 늘어나고, 착지할 때 눌렸다 돌아온다 |

### 꼭 지킬 것 (사장님) — **최고 높이와 최대 거리는 지금과 같게**

> *"곡선을 바꾸다 높이가 달라지면, 지난번처럼 못 닿는 발판이 생기거나 반대로 너무 쉬워집니다.
> 그러면 3번 칸에서 판 전체가 실패합니다."*

**그래서 그 둘을 재는 자를 회차 전에 만들었다** — `jump_measure.mts`.
상수(`jump: 13`, 중력 `0.62`)로 **계산하지 않는다**: 곡선을 바꾸면 중력이 구간마다 달라져
공식이 안 맞고, 그러면 자가 대리값이 된다. 헤드리스 창에서 **정말로 뛰게 하고 프레임마다 위치를 읽는다.**

| 원본 실측 | 값 |
|---|---|
| **최고 높이** | **117.4 px** |
| **최대 거리** | **168 px** |
| 곡선 | 상승 19프레임 · 꼭대기 4프레임 · 하강 21프레임 (전체 40) |
| 하강/상승 | **1.11** — 지금은 **내려오는 쪽이 더 느리다**(쫀득함의 반대) |

**3판 동안 같은 값이었다**(연달아 세 번 재서 전부 동일). 증명은 아니고 센 만큼이다.
공식으로 계산하면 136.3 px 이 나온다 — **실측과 19 px 다르다.** 공식으로 난간을 세웠으면 틀렸을 값이다.

회차는 **사장님 확인까지**이고, 다음 회차는 앞 회차 확인이 끝난 뒤에만 시작한다(개정판 5 ⑨).

### ㉠을 높이·거리 안 바꾸고 할 수 있나 — 할 수 있다

빠른 상승과 빠른 하강은 공중 시간을 **줄이고**, 공중 시간이 줄면 최대 거리도 줄어든다.
그런데 **꼭대기 체류는 공중 시간을 늘린다.** 그래서
`상승 ↓ + 꼭대기 ↑ + 하강 ↓` 으로 **전체 40프레임을 맞추면** 거리가 유지된다.
높이는 꼭대기 값을 그대로 두면 유지된다. 이것이 곧 사장님이 말한 곡선이다.
