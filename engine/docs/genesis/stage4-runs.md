> *"쫀득하다" 를 게임 손맛으로 풀면 대체로 **둥둥 뜨지 않고, 누른 대로 반응하고,
> 꼭대기에서 살짝 버티다 탁 떨어지는** 느낌입니다.*

| | 해석 항목 | 사장님 말 |
|---|---|---|
| ㉠ | **곡선 모양** | 빠르게 솟고, 꼭대기에서 아주 잠깐 머물고, 내려올 땐 올라갈 때보다 빠르게 떨어진다. **쫀득함의 핵심은 대부분 여기** |

| ㉢ | **관대함** | 발판 끝에서 살짝 늦게 눌러도 뛰어지고, 착지 직전에 미리 눌러 둔 점프도 먹힌다 |
| ㉣ | **보이는 탄력** | 뛸 때 살짝 늘어나고, 착지할 때 눌렸다 돌아온다 |

### 꼭 지킬 것 (사장님) — **최고 높이와 최대 거리는 지금과 같게**

> *"곡선을 바꾸다 높이가 달라지면, 지난번처럼 못 닿는 발판이 생기거나 반대로 너무 쉬워집니다.
> 그러면 3번 칸에서 판 전체가 실패합니다."*

**그래서 그 둘을 재는 자를 회차 전에 만들었다** — `jump_measure.mts`.

### ㉠을 높이·거리 안 바꾸고 할 수 있나 — 할 수 있다

빠른 상승과 빠른 하강은 공중 시간을 **줄이고**, 공중 시간이 줄면 최대 거리도 줄어든다.
그런데 **꼭대기 체류는 공중 시간을 늘린다.** 그래서
`상승 ↓ + 꼭대기 ↑ + 하강 ↓` 으로 **전체 40프레임을 맞추면** 거리가 유지된다.
높이는 꼭대기 값을 그대로 두면 유지된다. 이것이 곧 사장님이 말한 곡선이다.

# ⚠ 1회차에서 **자가 틀린 것이 드러났다** — 그리고 그 틀린 숫자가 사양이 됐다

## 무슨 일이 있었나

주문서에 *"절대 바꾸면 안 된다: 최고 높이 **117.4px**"* 라고 적어 보냈다. **그 값이 틀렸다.**

자가 `requestAnimationFrame` 으로 찍었는데 **내 표본이 게임 업데이트보다 먼저** 돌았다.
그래서 착지 프레임에서 발판에 붙기 **전의 초과분**을 읽었고, 땅 높이가 12.4px 아래로 잡혔다.
참값은 **129.8px** 이다.

고침은 내 숫자를 **충실히 구현했다** — 코드에 `117.4` 가 그대로 박혀 있다:

```js
if (player.jumpFrame <= 17) player.y = player.jumpStartY - 117.4 * (player.jumpFrame / 17);
else if (player.jumpFrame <= 25) player.y = player.jumpStartY - 117.4;
else player.y = player.jumpStartY - 117.4 * (1 - (player.jumpFrame - 25) / 15);
```

**결과: 실제 점프 높이가 12.4px 낮아졌다. 정확히 내 오차만큼이다.**
난간을 지키라고 준 숫자가 난간을 깬 원인이 됐다.

## 고친 자 (`jump_measure.mts`)

- **게임 틱에 맞춰 찍는다** — `draw` 를 감싼다(최상위 `function` 선언이라 덮어쓸 수 있고, `update()` 뒤에 불린다)
- **땅 높이를 점프 전에 찍는다** — 처음엔 "착지한 y" 로 잡았더니 착지 높이차가 정의상 늘 0 이 되어 **검사가 빈 껍데기**였다
- 착지 높이가 다르면 **거리는 '못 견준다'** 로 낸다

가로 이동은 안 건드렸다(`speed: 4.8` · 마찰 `0.78` 그대로). 그래서 **닿는 거리는 공중 프레임으로 본다** — 40 → 39.

## 두 가지가 각각 안 됐다

1. **난간**: 높이가 12.4px 낮아졌다. **원인은 내 틀린 숫자다** — 고침 탓이 아니다.
2. **㉠ 자체**: 사장님 해석은 *"내려올 땐 올라갈 때보다 빠르게"* 인데 **하강/상승이 1.11 → 1.44** 로
   더 느려졌다. 이건 내 숫자와 무관하게 요청을 못 맞춘 것이다.

그리고 방식이 **물리가 아니라 대본**이 됐다 — 17프레임 선형 상승 · 8프레임 정지 · 15프레임 선형 하강.
등속이라 가속감이 없고, 2회차(누르는 길이)를 얹기 어렵다.

### 새로 드러난 구멍 — **심판이 죽은 것이 결과물에 안 적힌다**

내가 `loop.stoppedBy` 를 따로 읽어서야 알았다.

오늘 여러 번 나온 **"자가 한 칸 모자라다"** 와 같은 모양이다.
결과물을 받는 쪽(사장님·나)이 **"이 판은 끝까지 못 봤다" 를 알 수 있어야 한다.**
→ 다음에 고칠 것: `stoppedBy` 가 `done` 이 아니면 결과물에 그대로 띄운다.


원본을 못 깼으므로 **조종이 서툰 것**이고 여기서 멈춘다(잠근 대로). 뛰는 자리를 여러 개 시도하게 고쳐 다시 잰다.

## 그런데 조종보다 큰 것이 나왔다 — **기계의 클리어와 사람의 클리어가 다르다**

**판 7 을 기계는 깼다.** 사장님이 직접 해 보고 *"높이가 높아서 클리어가 안돼"* 라고 하신 판이다.
**판 8 도 깼다.** 내 자가 *"올라가는 발판 쌍 여섯이 전부 막혔다"* 고 한 판이다.

짐작되는 이유(**추측**): 공중 55프레임에 가로로 264px 을 날아가니 **중간 발판을 오르지 않고 건너뛴다.**
깃발이 x 882 에 세로로 길게(y 155~465) 서 있어 바닥 높이에서도 닿는다.
즉 이 판에는 **오르지 않고 깨는 길**이 있고, 떠 있을수록 그 길이 쉬워진다.

### 이것이 흔드는 것 둘

1. **`못오르는발판` 난간이 게임이 요구하지 않는 길을 재고 있었을 수 있다.**
   판 4 부터 이 난간으로 "원본과 같아야 한다(1)" 를 걸었다. 그런데 그 1 이 **꼭 올라야 하는 길**인지 안 봤다.
   **확인 안 됨 — 다음에 잰다.**
2. **"깰 수 있다" 와 "깬다" 가 다르다.** 기계는 *깰 수 있는 길이 하나라도 있나*를 찾고,
   사람은 *보이는 길*로 간다. 사장님은 판 7 에서 중간 발판에 내려앉으려다(착지여유 −26.8) 떨어지셨을 것이다 — **추측이다.**
   기계가 찾은 건너뛰기 길은 사람에게 **안 보였거나, 보였어도 게임으로 안 느껴졌을** 수 있다.

> **눈을 달았더니, 사람과 다른 것을 봤다.**
> 3번 칸을 기계로 넘기려면 *"깰 수 있나"* 가 아니라 **"사람이 가는 길로 깨지나"** 를 재야 한다.
> 그 길이 무엇인지는 — 다시 사람 말에서 나온다.

지금까지 기계 클리어 vs 사람 판정: **판 6 맞음 · 판 7 어긋남 → 2판 중 1판.**
## ⚠ 전제가 틀렸다 — **원본은 사장님이 깨신 판이 아니다** (2026-09-23 새벽)

끝까지 해 보는 기계가 원본을 못 깨서(무대 2 에서 세 번 다 죽음) 추적했다.

발판 5(x 735)는 235px 너머라 못 닿는다. **기하로 무대 2 가 안 깨진다.**

그래서 *"원본은 사장님이 깨신 판"* 이라는 전제를 확인했다. **틀렸다.**

```

```

**무대 2 의 발판 4 가 50px 위로 올라가 있다.** 물리 상수는 같다.
06:59 이후의 판은 전부 "글자만 고친" 판이었다(클리어 화면 단추 글자 · 제목 글자 두 번) — **그중 하나가 발판을 건드렸다.**
어느 판인지는 재는 중.

### 이것이 뒤집는 것

1. **"원본의 못오름 1" 은 필요 없는 길이 아니라 회귀 버그였다.**
   나는 판 4 부터 *"원본과 같게 = 1"* 을 난간으로 걸었다. **버그를 난간으로 잠근 것이다.**
2. **판 1~8 의 3번 칸에는 '되던 것' 이 없었다.** 원본부터 무대 2 를 못 깬다.
   사장님이 판 6·7 에서 *"클리어가 안돼"* 라고 하신 것은 **그 판들이 원본의 회귀를 그대로 물려받아서**일 가능성이 크다.
   → 내가 판 6 에 붙인 진단(**착지 여유 6.8px**)은 **원인이 아닐 수 있다.** 추측으로 내린다.
3. **기계가 판 7·8 을 깬 이유**도 이것으로 설명된다: 공중 49·55 프레임이면 발판 2 → 4 를 **한 번에** 건너뛴다(215px).
   떠 있을수록 회귀 버그를 우회한다. 기계는 "깰 수 있는 길" 을 찾았고, 그 길은 **버그가 열어 준 길**이었다.

### 배운 것 — **"글자만 고친다" 는 판도 '되던 것' 을 잰다**

09-08 의 *"안 지어진 게임이 합격했다"*, 09-21 의 *"자가 침묵하면 심은 것을 먼저 의심한다"* 와 같은 자리다.

*(원본을 어떻게 할지 — 깨신 판으로 되돌릴지, 지금 원본을 고칠지 — 는 사장님 몫. 판 1~8 의 판정은 소급해서 안 바꾼다.)*

### 부탁 심판이 통과시켰다 — "다른 부분은 건드리지 않았습니다"

**발판이 옮겨졌는데 부탁 심판은 "다른 부분은 안 건드렸다" 고 했다.**

### (가) 와 (나) 는 **제목 글자 한 줄**만 다르다

깨신 판(0b2b6f97) → 원본(3e9de329) 의 전체 diff 는 **2줄**뿐이다:

```

```

즉 **(나) = 깨신 판 + 큰 제목**이다. "클리어 화면 단추 글자 수정" 판의 흔적은 최종 diff 에 없다.
사장님이 고르실 것은 사실상 *제목을 키운 채로 갈지*뿐이다.
### 실제 diff — "제목만" 주문이 **3줄**을 바꿨고 그중 **2줄이 주문과 무관**하다

0bff69f3(단추 글자) → cfbc57c5(제목 글자):

```

156: 발판 4  { x: 545, y: 350 } → { x: 545, y: 300 }                       ← 주문 안 함 · 회귀
215: restartButton "클리어!" → "클리어"                                     ← 주문 안 함 · 앞 판이 고친 것을 도로 되돌림
```

**부탁 심판은 이 3줄짜리 diff 를 보고 "다른 부분은 건드리지 않았습니다" 라고 통과시켰다.**
3줄 중 2줄을 못 봤거나 보고도 넘겼다. diff 가 길어서가 아니다 — **세 줄이었다.**

215 번 줄은 더 뼈아프다: 바로 앞 판(0bff69f3)이 *"클리어 화면 단추 글자 수정"* 으로 고친 것을 **다음 판이 도로 되돌렸다.**
앞 판의 고침이 사라졌는데 아무도 몰랐다. **회차마다 "지난 회차의 고침이 남아 있나" 도 재야 한다.**

### 되돌림 검사를 기계로 (09-23) — `revertCheck.ts` · 5/5

"제목만" 판이 앞 판의 고침("클리어!")을 도로 되돌렸는데 부탁 심판이 통과시킨 구멍을 **기계가 잡게** 했다.
앞앞·앞·이번 세 판을 줄 단위로 대 본다: 앞 판이 넣은 줄이 이번 판에서 사라지고 앞앞 판의 줄이 다시 나타나면 되돌림이다.

```
맞음  앞 판의 고침이 되돌려진 것을 잡는다        ← 실제 세 판(깨신 판 → 단추 글자 → 제목 글자)
맞음  되돌아간 줄이 '클리어' 단추 줄이다
맞음  고침이 살아 있으면 안 잡는다
맞음  앞 판이 안 고쳤으면 0
맞음  공백만 달라진 줄은 안 잡는다
```

**아직 고리에는 안 꽂았다.** 꽂으려면 이번 판이 "앞앞 판" 을 알아야 한다(앞 판의 앞 판). 그 연결이 결과물에 남는지 확인 중.
### 되돌림 검사를 고리에 꽂았다 (09-23)

- `lineage = { prev, prevPrev }` 를 고리에 넘긴다. **앞앞 판**은 앞 판 업무의 `previousDeliverableId` 로 찾는다.
- 바퀴마다 `revertBroken(prevPrev, prev, files)` → 문장이 나오면 `verdict.broken` 에 얹는다 → 고치는 자리가 다음 바퀴에 본다.
- 앞앞 판이 없으면(첫 고침·연결 안 남음) **못 잼**으로 로그를 남기고 조용히 빠진다. 통과가 아니다.

고리 꼴로 실제 세 판에 대 본 것:

```
맞음  고리 꼴로도 잡힌다: 되돌림: 앞 판이 고친 줄이 사라졌다 — "restartButton.textContent = title === "클리어!" ? …"
                        (앞앞 판의 "… title === "클리어" ? …" 로 돌아감)
맞음  살아 있으면 0
맞음  앞앞 판 없으면 조용히 0(못 잼)
```

**한계**: 줄 단위·집합이라 **같은 줄이 다른 자리로 옮겨진 것**은 못 본다(살아 있다고 본다).
그리고 이 검사는 **되돌림**만 본다 — "주문에 없는 줄이 바뀌었다"(발판 y 350→300 같은 것)는 **아직 안 본다.**
그건 끝까지 해 보기(`게임.클리어`)가 결과로 잡는다. 두 자가 서로 다른 구멍을 막는다.
### 감시가 다섯 번 침묵했다 — `wmic` 가 없었다 (09-23)

기계가 비면 알리라고 감시를 일곱 번 걸었다. **세 번째부터는 `wmic` 로 바꿨는데, 이 윈도우(26200)에는 `wmic` 가 없다.**
`free` 가 빈 값 → 0 MB → 조건이 영영 참이 안 됨. **다섯 번(약 2시간 반)은 아무것도 안 재고 있었다.**
나는 그 침묵을 "기계가 계속 꽉 차 있다" 로 읽었다.

09-21 사장님 말 그대로다: *"도구가 '0' 이라고 할 때도 똑같이 의심하라."* 이번엔 0 도 아니고 **아무 말도 없었다.**
감시를 걸 때 **첫 판독을 한 번 눈으로 확인**했어야 했다 — 처음 두 번(PowerShell)은 숫자가 찍혔고, 바꾼 뒤엔 안 봤다.

다시 잰 실측(PowerShell): **남은 메모리 862 MB · CPU 100%** — 결론(기계 포화)은 그대로다. 다만 근거는 이 한 줄이고, 다섯 번의 침묵이 아니다.
