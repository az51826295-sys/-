# 우리가 부르는 이름이 다른 모델로 넘어간다 (2026-09-21)

## 잰 것

토큰 1개짜리 호출로 **응답이 스스로 말한 이름**을 받아 봤다(값 거의 0).

| 부른 이름 | 응답이 말한 이름 |
|---|---|
| `deepseek-v4-flash` | **`deepseek-flash`** |
| `deepseek-chat` | **`deepseek-flash`** |
| `deepseek-flash` | `deepseek-flash` |
| `deepseek-v4-pro` | `deepseek-v4-pro` |

**우리가 쓰는 이름 둘이 별칭**이고 같은 모델로 넘어간다. 목록 API 가 둘만 보여 주던 이유도 이것이다.

## 원장으로는 못 잡는다

`model_usage.model` 은 **우리가 부른 이름**이지 응답이 돌려준 이름이 아니다(`meter.ts` 의 `result.model`
이 요청 변수다). 그래서 *"124건의 model 칸을 날짜별로 세면 바뀐 날이 보인다"* 는 **안 된다.**
바뀐 날을 보려면 응답의 이름을 원장에 남겼어야 했다.

## 그래서 못 아는 것 (중요)

**별칭이 가리키는 모델이 언제 바뀌었는지 모른다.** 조사한 날짜로는 DeepSeek V4.1 Flash 가 09-10 에
나왔고, 우리 표본은 09-19(옛 고침 10판)와 09-21(오늘 2단계)이다. 둘 다 09-10 이후라 **한 모델일
가능성이 높지만, 기록이 없어 확인할 수 없다.** "높다" 로 적고 "확인됨" 으로 적지 않는다.

2단계 판정에 미치는 범위: 그 비교는 **자리 고르는 방식**(머리가 고름 vs 섞음)이지 모델끼리가 아니다.
다만 섞는 쪽이 이 별칭을 집을 때가 있으므로, **섞은 팔의 구성이 중간에 바뀌었을 가능성**은 남는다.
판정은 어차피 "모름" 이므로 결론은 안 바뀐다.

## 알림이 끊긴 원인 — **추정**

09-18·19 에는 *"쓰는데 사라졌다"* 알림이 떴고 09-20 부터 안 뜬다. 이름 가족 맞추기가
`deepseek-v4-flash` 를 `deepseek-flash` 의 가족으로 쳐서 삼킨 것으로 **보인다.**
맞추기 코드가 그대로였는지, DeepSeek 목록이 그날 바뀌었는지는 **안 봤다.** 그래서 **추정**이다.

## 다음에 할 일 (오늘은 안 고침)

1. **응답이 돌려준 이름을 원장에 남긴다.** 지금은 우리가 부른 이름만 남아 별칭 이동을 영영 못 본다.
2. 눈이 보는 곳을 넓힌다 — Gemini 는 열쇠가 있는데 안 본다. 영상 모델도 목록에 안 잡힌다.
3. 옮겨 갈지 정할 때는 **회사 공식 변경 기록**에서 한 번 더 본다. 오늘 날짜는 모아 보는 사이트에서 왔다.

## 이어서 (2026-09-22 새벽) — 칸을 만들었다. 다만 **어디까지 쟀는지**를 정확히

새 토큰으로 `model_usage` 에 두 칸을 더했다: **`answered_by`** 와 **`answered_fingerprint`**.

### 왜 두 칸인가

이름 하나로는 부족하다 — **같은 이름 뒤에서 모델이 바뀌면 이름은 그대로다.** 실제로 확인했다:

| 부름 | 응답이 말한 이름 | 지문 |
|---|---|---|
| `gpt-5.6-luna` (OpenAI) | `gpt-5.6-luna` | **없음(null)** |
| `deepseek-v4-flash` (DeepSeek) | `deepseek-flash` | **`aeb56401…`** |

정작 알고 싶은 것이 DeepSeek 별칭인데 **DeepSeek 은 지문을 준다.** 그래서 지문 칸을 같이 만들었다.

### 어디까지 쟀나 (사장님 09-22)

| | 상태 |
|---|---|
| 공급자가 응답 이름을 들고 온다 | **확인**(OpenAI 로 진짜 호출) |
| DeepSeek 이 이름·지문을 준다 | **확인**(직접 호출) |
| 계량기를 거쳐 **원장에 찍힌다** | **미확인** |
| DeepSeek 호출이 **우리 공급자 길로** 이름·지문을 싣는다 | **미확인** |

시험 호출은 회사 범위가 없어 원장에 안 적힌다. 그래서 **다음 실제 판에서 DeepSeek 행 한 줄을 눈으로 확인**해야 한다.
그 전에는 "원장까지 흐른다" 고 적지 않는다. (내가 한 번 그렇게 적었고, 그건 잰 것보다 앞선 말이었다.)

### 이미 쌓인 것은 여전히 모른다

새 칸은 **앞으로 생기는 행**에만 찬다. 이미 있는 124건은 비어 있다.
그러므로 **09-21 에 못 알아낸 "별칭이 언제 넘어갔나" 는 지금도 모른다.** 이제부터의 변화만 잡을 수 있다.

### 지문을 어떻게 읽을 것인가 (사장님 09-22)

**지문은 모델보다 넓은 것을 가리킨다.** 보통 서버 설정 전체를 나타내므로, **모델이 그대로여도 설정이 바뀌면 달라질 수 있다.**
그러므로 **한쪽 방향만 믿는다:**

| 관측 | 읽는 법 |
|---|---|
| 지문이 **바뀌었다** | 뭔가 달라졌다 → **살펴본다.** 모델이 바뀐 것일 수도, 설정만 바뀐 것일 수도 있다 |
| 지문이 **그대로다** | 같은 설정이다. **"같은 모델" 이라고까지는 말하지 않는다** |

### 호출마다 같은가 — **같다**(확인함)

여러 서버에 나뉘어 돌면 지문이 매번 달라지고, 그러면 변화를 잡는 데 못 쓴다. 그래서 먼저 쟀다.
같은 이름으로 세 번 부르니 **세 번 다 `aeb56401…`** 이었고, **09-21 에 찍힌 값과도 같았다.**
그러므로 이 칸은 쓸 수 있다.

(OpenAI 는 지문을 안 준다 — 그쪽은 이름 칸만으로 봐야 한다.)

## 이번 배포에 함께 나가는 것 (2026-09-22 09:1x)

대기열 수정 하나를 올리려고 **여러 커밋이 한꺼번에** 나간다. 그중 **처음 도는 것**을 적어 둔다 —
다음 실제 판에서 확인할 목록이다(사장님 09-22).

| 커밋 | 처음 도나 | 다음 판에서 볼 것 |

| 응답 모델 이름·지문 배선(`answered_by`·`answered_fingerprint`) | **예** | 원장 행에 두 칸이 **찍히는지** · DeepSeek 행의 지문이 `aeb56401…` 인지 |
| 검토 대기열을 다 읽게(`readFiltered`) | **예** | 1000줄 넘어도 안 잘리는지(지금은 949줄이라 아직 안 보인다) |

**주의**: 지문 칸 배선은 어젯밤 것이라 **한 번도 안 돌았다.** "코드 연결됨 · 원장 기록 미확인" 으로 적어 둔 그것이다.

## 확인했다 — 그리고 **절반만 돌았다** (2026-09-22 11:0x)

위 표의 첫 줄을 실제 판으로 확인했다(데모 회사, 작은 고치는 판 하나). 원장:

```
gpt-5.6-luna      → gpt-5.6-luna · (빔) · loop_verdict
gpt-5.6-luna      → gpt-5.6-luna · (빔) · ask_verdict
deepseek-v4-flash → (빔) · (빔) · app_patch
deepseek-v4-flash → (빔) · (빔) · app_patch
gpt-5.6-luna      → gpt-5.6-luna · (빔) · ask_verdict
deepseek-v4-flash → (빔) · (빔) · app_patch
deepseek-v4-flash → (빔) · (빔) · app_plan
deepseek-v4-pro   → (빔) · (빔) · head_decision
응답 이름이 찍힌 줄 3/8
```

**정작 보려던 쪽이 비어 있었다.** 이 칸을 만든 이유가 딥시크 별칭이 언제 움직이는지 보려는 것이었는데,
찍힌 셋은 전부 luna 였고 딥시크 다섯 줄은 이름·지문 둘 다 빔이었다.

원인: **공급자가 한 파일이 아니었다.** 나는 `providers/openai.ts` 의 `responses.parse` 길에만 넣었고,
딥시크는 `providers/deepseek.ts` 의 `chat.completions.create` 를 쓴다(앤트로픽은 또 다른 파일).
09-21 에 딥시크를 **직접 불러** 지문을 받은 것은 이 배선을 하나도 지나지 않는 길이었다.

배울 것: **호출이 지나는 길이 몇 개인지 먼저 센다.** 한 길에 넣고 자를 대면
자가 말한 "찍힌다" 는 내가 고친 길에 대한 답일 뿐이다. 3/8 을 한 덩어리로 세서
"배선 됨" 으로 읽은 것도 같은 잘못이다 — 그래서 자(`answered_check.mts`)를
**공급자별로 갈라 세게** 고쳤다. 한 덩어리로 세면 luna 가 딥시크의 0 을 덮는다.

## 딥시크 줄이 찍혔다 — 그리고 **별칭은 flash 만 접힌다** (2026-09-22, 판 `7e52c7ec`)

세 공급자 파일에 다 배선하고 다시 돌린 원장:

```
deepseek-v4-pro   → deepseek-v4-pro · a307abda… · head_decision
deepseek-v4-flash → deepseek-flash  · aeb56401… · app_plan
deepseek-v4-flash → deepseek-flash  · aeb56401… · app_patch
gpt-5.6-luna      → gpt-5.6-luna    · (빔)      · ask_verdict
deepseek-v4-flash → deepseek-flash  · aeb56401… · app_patch
gpt-5.6-luna      → gpt-5.6-luna    · (빔)      · ask_verdict

deepseek: 이름 4/4 · 지문 4/4
gpt-:     이름 3/3 · 지문 0/3   (이 API 는 지문을 안 준다)
claude:   이번 판에 줄이 없다 — **못 잼**
```

**이제 원장까지 흐른다** — 딥시크는 이름·지문 둘 다, OpenAI 는 이름만.
앤트로픽은 배선은 했지만 이번 판에 안 불렸으므로 **'통과' 가 아니라 '못 잼'** 이다.

새로 나온 것 둘:

1. **접히는 대상은 flash 하나지만, 접히는 이름은 둘이다.**
   `deepseek-v4-flash` 와 `deepseek-chat` 이 **둘 다** `deepseek-flash` 로 답한다(09-21 실측).
   반대로 `deepseek-v4-pro` 는 **자기 이름 그대로** 답한다.
   09-21 에 "딥시크가 별칭을 접는다" 고 딥시크 전체에 적었는데, 접는 것은 싼 자리 하나였다.

2. **지문은 flash 안에서는 안 흩어진다. pro 는 아직 못 잼** (사장님 09-22 정정).
   처음에 *"모델마다 다르니 서버별로 흩어지는 값이 아니다"* 라고 적었는데 **한 단계 앞선 말이었다** —
   서로 다른 모델이 다른 값을 내는 것은 **지문이 서버 설정을 가리키는 값이어도 똑같이 나온다.**
   흩어지지 않는다는 근거는 **한 모델을 여러 번 불러 매번 같은 값**이 나온 것뿐이다. 실제로 센 것:

   | 부른 이름 → 답한 이름 | 원장 줄 | 지문 | 판정 |
   |---|---|---|---|
   | `deepseek-v4-flash` → `deepseek-flash` | **3줄** | `aeb56401…` ×3 | 이 모델 안에서는 **안 흩어진다** |
   | `deepseek-v4-pro` → `deepseek-v4-pro` | **1줄** | `a307abda…` ×1 | **못 잼 — 한 줄뿐이다** |

   flash 는 09-21 에 직접 부른 3회도 같은 값이었고 그 값이 09-21 원장 값과도 같았다
   (다만 그 3회는 회사 범위가 없어 **원장 밖**이다). pro 는 판을 더 돌려야 한다.
   자: `fp_count.mts` — 한 모델 안에서 줄이 2개 미만이면 **'같다' 가 아니라 '못 잼'** 으로 낸다.

## 지문을 어느 쪽으로 믿나 (사장님 09-22)

**한쪽 방향만 믿는다.** 어제 그은 선과 같다:

- 지문이 **안 바뀌었다** → 같은 모델·같은 설정이다. (믿는다)
- 지문이 **바뀌었다** → 모델이 갈렸을 수도 있고, **같은 모델의 서버 설정만 바뀐 것**일 수도 있다.
  → **살펴본다.** "모델이 갈렸다" 로 바로 읽지 않는다.

이름 칸도 같다 — 이름이 그대로라고 같은 모델인 것은 아니다(별칭이 접히는 자리가 그 증거다).
그래서 두 칸은 **문이 아니라 살펴볼 거리**다.
