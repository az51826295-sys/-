# Phase 3 검토 — World Model v0.1

Phase 3에는 프로젝트 전체의 방향을 가르는 결정 두 개가 숨어 있다.
둘 다 문서에 명시되지 않은 채로 지나가고 있어서, 구현에 들어가는
순간 갈린다.

---

## 결정 ① — 세계모델은 "무엇"으로 만들어지는가

문서는 `Transition Model`, `State Encoder` 같은 학습된 신경망의
어휘로 쓰여 있다. 그런데 실현 방법은 두 가지고, 서로 완전히 다른
프로젝트다.

| | (i) 학습된 세계모델 | (ii) 명시적 세계모델 |
|---|---|---|
| 형태 | 신경망 파라미터 | DB에 저장된 규칙·확률·그래프 |
| 만드는 법 | 대량 데이터로 훈련 | 경험에서 규칙 추출, LLM이 추론 엔진 |
| 필요 자원 | GPU, 수개월, 대량 상호작용 | 현재 인프라로 가능 |
| 검사 가능성 | 불가 | 가능 |
| 수정 가능성 | 재훈련 | 행 하나 수정 |

### Genesis의 원칙들이 이미 (ii)를 요구하고 있다

이게 핵심이다. 10원칙과 Phase 2·3이 요구하는 것들을 보면:

- 모든 지식에 **신뢰도**가 있어야 한다
- 모든 지식에 **출처**(REAL/IMAGINED/REPORTED)가 있어야 한다
- 모순을 **발견하고 분기**해야 한다
- 규칙을 **폐기**할 수 있어야 한다
- 실패를 **원인별로 분류**해야 한다

> **신경망 가중치에는 출처를 붙일 수 없고, 신뢰도를 조회할 수 없고,
> 특정 믿음 하나만 폐기할 수 없다.**

즉 Genesis의 철학은 기술적으로 (ii)를 강제한다. 이건 타협이 아니라
설계의 논리적 귀결이다. 문서를 (ii)의 언어로 다시 쓰는 것을 권한다.

역할 분담은 이렇게 된다:

```
LLM        = 추론 엔진 (규칙을 적용하고, 가설을 만들고, 언어를 다룸)
세계모델   = 검증된 규칙의 저장소 (신뢰도, 출처, 반례를 가진)
Genesis    = 둘 사이의 루프 (예측 → 검증 → 규칙 수정)
```

LLM은 교체 가능한 부품이 된다. 축적되는 자산은 세계모델 쪽에 쌓인다.
이게 "우리 AI"가 실제로 우리 것이 되는 지점이다 — 모델을 훈련해서가
아니라, **모델이 갖지 못한 검증된 규칙 집합을 우리가 소유**해서.

## 결정 ② — Genesis의 "세계"는 어디인가

16절의 프로토타입은 격자방·문·열쇠·에너지다. 여기에 두 가지 문제가
있다.

### 문제 1 — 그 세계에서 성공해도 아무것도 증명되지 않는다

격자 미로에서 문을 열고 열쇠를 찾는 것은 강화학습이 수천 번 푼
문제다. Genesis가 거기서 잘 해도 "기존 방법으로 이미 되는 걸 더 비싸게
했다"가 된다.

### 문제 2 — 전이되지 않는다

문·열쇠 세계에서 배운 인과 규칙은 회사 업무로 옮겨가지 않는다.
그리고 앱에 넣겠다고 한 이상, 최종 목적지는 업무 세계다.

### 대안 — Rookery의 업무 세계가 Genesis의 첫 세계다

| 세계모델 요소 | 격자방 | Rookery |
|---|---|---|
| 상태 | 좌표, 문 상태 | 회사 상황, 직원 역량, 업무 조건, 기존 지식 |
| 행동 | 이동, 열기, 집기 | 어떤 접근으로 업무를 수행할지 |
| 결과 | 문이 열림 | 매니저 승인 / 수정 요청 / 반려 |
| 숨은 상태 | 잠김, 고장 | 매니저의 암묵적 기준, 말하지 않은 맥락 |
| 다른 에이전트 | 없음 | **매니저 — 실재하고, 예측 어렵고, 중요함** |
| 인과 규칙 | 열쇠→문 | 어떤 조건에서 어떤 방식이 승인받는가 |

**9절의 "숨은 상태 추론"이 여기서 진짜가 된다.** 매니저가 왜 반려했는지는
직접 보이지 않는다. 가설이 여러 개고, 구분 실험(다음 업무에서 한 가지만
바꿔보기)이 실제로 가능하다. 문이 안 열리는 이유를 추론하는 것보다
훨씬 어렵고 훨씬 가치 있다.

**12절의 Agent Model도 마찬가지다.** 가상의 `player_02`가 아니라
실제 매니저의 목표·기준·선호를 추정하는 문제가 된다. Rookery는 이미
`manager_preference` 카테고리로 그 일부를 하고 있다 — 다만 예측
없이, 사후 추출로만 한다.

## 3. 반사실 시뮬레이션은 예산을 파괴한다

5절: 행동 후보를 여러 개 만들고 각각의 미래를 시뮬레이션한다.

LLM 위에서 이건 업무 한 건당 호출 수의 3~10배를 의미한다. 회사당
30일 $3 한도에서 매 업무마다 여러 미래를 돌리면 **첫 주에 예산이
소진되고 실제 업무는 한 건도 못 한다.**

### 시뮬레이션은 조건부여야 한다

```
IF  예측 불확실성이 높다        AND
    행동이 되돌리기 어렵다      AND
    실패 비용이 시뮬레이션 비용보다 크다
THEN 시뮬레이션한다
ELSE 그냥 한다
```

싼 결정은 그냥 하고 결과에서 배우는 게 더 싸다. 되돌릴 수 있는
실패는 최고의 학습 수단이고, 시뮬레이션보다 정확하다.

> 이게 Existence Drive의 Cost 항이 실제로 설계를 바꾸는 첫 사례다.
> 예산이 없으면 "항상 시뮬레이션"이 최적이 되고, 그건 곧 마비다.

**"언제 상상하고 언제 그냥 할 것인가"를 결정하는 정책 자체가 학습
대상**이어야 한다. 이건 제8원칙(전략 수정)의 가장 구체적인 사례다.

## 4. 6절(상상/현실 구분)은 이 문서에서 가장 중요한 부분이다

`REAL / SIMULATED / IMAGINED / REPORTED` 구분은 정확하다. 이게
없으면 AI가 자기 상상을 근거로 자기 믿음을 강화하고, 몇 사이클 안에
현실과 무관한 정합적 환상에 도달한다.

### 다만 컬럼 하나로는 부족하다

`source_type` 컬럼으로 구분하면 **언젠가 필터를 빠뜨린다.** 회상
쿼리, 통계 쿼리, 학습 추출, 리포트 — 한 곳만 놓쳐도 오염된다.

권장:

```
경험 테이블      → REAL 만 들어간다. 물리적으로 다른 테이블.
상상 테이블      → IMAGINED / SIMULATED
지식 테이블      → 출처와 근거 경험 id를 참조
```

**IMAGINED에서 나온 것은 REAL 경험 테이블에 절대 승격되지 않는다.**
검증되면 새 REAL 경험이 기록되고, 상상은 그 예측이었던 것으로 남는다.
승격 경로를 아예 만들지 않는 게 안전하다.

## 5. 불확실성 3종은 좋지만 구분 방법이 없다

7절의 환경/지식/관찰 불확실성 구분은 옳고 중요하다. (지식
불확실성만이 학습으로 줄어들고, 나머지에 학습 비용을 쓰면 낭비다.)

문제는 LLM에게 "이건 어떤 종류의 불확실성인가"를 물어보면 그럴듯한
답을 하지만 그건 측정이 아니라는 것이다.

### 실제로 구분하는 방법 — 재현 실험

```
같은 조건에서 반복했을 때
  결과가 갈린다   → 환경 불확실성 (배워도 안 줄어듦, 포기)
  결과가 일관된다 → 지식 불확실성 (배우면 줄어듦, 여기에 투자)
```

이건 계산 가능하고, Phase 1의 LP와 정확히 같은 것을 측정한다.
**LP가 0인 영역이 곧 환경 불확실성 영역이다.** 두 개념이 같은
수치로 만난다.

## 6. 시간 규모(13절)를 도메인에 맞게 다시

0.1초 단위는 이 도메인에 존재하지 않는다. 실제 규모:

| 규모 | Rookery에서 | 이미 있는 것 |
|---|---|---|
| 즉시 | 업무 1건 결과 | 실행 엔진 |
| 단기 | 수정 요청 사이클 | revisions |
| 중기 | 주간 운영 사이클 | operating_cycles |
| 장기 | 분기 계획 결과 | planning |

**세계모델의 시간 층을 새로 발명할 필요가 없다.** 이미 있는 사이클
구조에 예측을 붙이면 된다. 각 층에서 "다음 사이클에 무엇이 일어날
것인가"를 예측하고 실제와 비교한다.

## 7. 성공 기준에 기준선이 없다

18절의 여섯 기준은 전부 "AI가 ~를 한다" 형태다. 그런데 **무엇보다
잘해야 성공인지**가 없다. 기준선 없이는 어떤 결과도 성공으로 읽힌다.

### 반드시 필요한 두 기준선

```
기준선 A : 현재 Rookery (예측 없음, 사후 학습만)
기준선 B : 세계모델 없이 LLM에게 그냥 물어본 예측
```

**기준선 B가 냉정하지만 결정적이다.** 세계모델이 "그냥 LLM에게
물어보기"보다 예측을 잘하지 못하면, 그 세계모델은 존재하지 않는
것과 같다. 비용만 더 쓴 것이다.

Phase 3의 진짜 성공 기준은 이 한 줄로 줄일 수 있다:

> **축적된 규칙을 쓴 예측이, 같은 LLM의 맨몸 추측보다 캘리브레이션과
> 정확도에서 유의하게 낫다.**

그리고 그 격차가 **시간이 갈수록 벌어져야** 한다. 벌어지지 않으면
축적이 일어나지 않는 것이고, 축적이 없으면 Genesis가 아니다.

## 8. 인과 vs 상관(10절)에 대한 현실적인 한계

인과 구조를 학습하려면 개입(intervention)이 필요하다 — 다른 조건을
고정하고 한 가지만 바꿔서 결과를 보는 것. 관찰만으로는 원리적으로
인과를 확정할 수 없다.

Rookery에서 개입은 **가능하지만 비싸다.** 실제 업무 하나가 실험
하나이므로, 실험 설계는 신중해야 한다. 표본이 수천 건이 아니라 수십
건 규모라는 것을 전제로 설계해야 한다.

현실적 목표: 인과 그래프를 완성하는 게 아니라, **명백한 교란 변수를
가진 상관을 규칙으로 승격시키지 않는 것.** 규칙 승격 조건에 "다른
조건이 달랐던 환경에서도 성립했는가"(`tested_environments`)를 넣는
15절 방향이 맞다.
