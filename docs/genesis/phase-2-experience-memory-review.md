# Phase 2 검토 — Experience Memory v0.1

구조는 옳다. 아래 일곱 가지는 지금 고치면 한 줄이고, Phase 3 이후에
고치면 전면 재작업이 되는 것들이다.

---

## 1. 저장 시점에는 그 경험의 가치를 알 수 없다

제안된 공식:

```
기억 가치 = 새로움×0.25 + 정보획득×0.25 + 목표관련성×0.20
          + 예측오류×0.15 + 재사용가능성×0.15
```

문제는 가중치가 임의값이라는 게 아니다. **"재사용 가능성"을 저장
시점에 알 수 없다**는 것이다. 어떤 경험이 가치 있었는지는 나중에
드러나고, 그때는 이미 버린 뒤다.

그리고 이 공식은 값비싼 실수를 유도한다. 사소해 보였던 관찰이 3개월
뒤 결정적 반례가 되는 일은 드물지 않고, 정확히 그런 경험이 낮은
점수를 받는다 (새로움 낮음, 예측오류 낮음).

### 대안 — 사후 효용(retrospective utility)

```
저장 시점 : 싸게, 전부 저장한다. 판단하지 않는다.
사후      : "이 경험이 실제로 이후 예측을 개선했는가"를 누적 갱신한다.
망각      : 사후 효용이 낮은 것부터, 지연해서 압축한다.
```

경험 한 건의 원본은 텍스트 수 KB다. 저장 비용보다 **잘못 버린 비용이
훨씬 크다.** 판단을 미룰 수 있으면 미루는 게 맞다.

사후 효용은 계산 가능하다: 어떤 경험이 회상되어 예측에 사용됐고, 그
예측의 오차가 낮았는가. 회상 로그만 남기면 자동으로 나온다.

---

## 2. 채워질 수 없는 필드가 섞여 있다

예시 스키마의 숫자들이 어디서 오는지 확인해 보면 세 종류로 나뉜다.

| 필드 | 계산 주체 | v0.1 가능 여부 |
|---|---|---|
| `prediction_error` | 예측 vs 결과 비교 | **가능** |
| `success` | 매니저/현실 | **가능** |
| `information_gain` | 세계모델의 사전/사후 엔트로피 차 | **Phase 3 필요** |
| `novelty` | 기존 경험 분포와의 거리 | 부분 가능 (임베딩 거리) |
| `confidence` (learning) | ? | **위험 — 아래 참조** |
| `reward` | ? | 정의되지 않음 |

`information_gain`은 세계모델이 있어야 정의된다. Phase 3 이전에는
채울 수 없다. **그런데 Phase 2 스키마에 필드로 들어가 있으면 LLM이
그냥 그럴듯한 숫자를 적어 넣는다.** 그 순간 이건 측정이 아니라
자기보고고, 자기보고된 0.71은 아무것도 아니다.

### 규칙

> **계산할 수 없는 필드는 v0.1 스키마에서 뺀다.**
> 나중에 Phase 3에서 추가한다. 빈 칸이 가짜 숫자보다 낫다.

v0.1이 실제로 채울 수 있는 것: context, goal, prediction(+확률),
action, observation, prediction_error, success, cost, lesson,
verification 상태. 이걸로 충분하다.

`reward`는 아예 빼는 걸 권한다. 정의되지 않은 보상 신호는 나중에
목적함수와 충돌하는 두 번째 목적함수가 된다.

---

## 3. 예측 잠금이 스키마에 없다 (가장 중요)

`prediction` 필드는 있는데 **언제 쓰였는지에 대한 보장이 없다.**

결과를 본 뒤에 예측을 적을 수 있다면 `prediction_error`는 의미 없는
숫자다. 그리고 LLM 파이프라인에서 이건 실수로 매우 쉽게 일어난다 —
한 번의 호출로 예측과 결과 해석을 같이 생성하면 끝이다.

### 요구사항

```
1. 예측은 행동 이전에 별도 쓰기로 커밋된다 (같은 호출 안에서가 아니라)
2. prediction_committed_at 은 서버 타임스탬프
3. 예측 행은 append-only — UPDATE/DELETE 금지 (DB 권한 수준에서)
4. 결과는 별도 행으로 붙는다. 예측 행을 수정하지 않는다.
```

Supabase에서는 RLS와 트리거로 강제 가능하다. **애플리케이션 코드의
약속이 아니라 DB 제약이어야 한다.** 코드는 언젠가 잊는다.

---

## 4. confidence는 캘리브레이션되지 않으면 장식이다

`"confidence": 0.63`, `"probability": 0.72` 같은 숫자는 그 자체로는
아무 정보가 없다. 검증되어야 정보가 된다:

> **0.7이라고 말한 예측들 중, 실제로 70%가 맞았는가.**

이 측정(Brier score / 캘리브레이션 곡선)이 없으면 LLM은 거의 항상
과신한다. 그리고 과신하는 세계모델은 틀린 세계모델보다 위험하다 —
언제 실험해야 하는지를 모르게 되기 때문이다.

Phase 2 v0.1에 반드시 들어가야 하는 것: 확률 예측의 버킷별 적중률
집계. 테이블 하나와 뷰 하나면 된다.

---

## 5. 기억 6층은 v0.1에 과하다

6층 분류 자체는 옳다. 다만 지금 환경에서 실체가 있는 층과 없는 층이
갈린다.

| 층 | Rookery 환경에서 | v0.1 |
|---|---|---|
| 감각 기억 | 실시간 센서가 없다. 실체 없음 | **보류** |
| 작업 기억 | 실행 컨텍스트가 이미 그 역할 | **기존 것 사용** |
| 사건 기억 | 핵심 | **구현** |
| 의미 기억 | 핵심 | **구현** |
| 절차 기억 | 의미 기억의 특수형으로 시작 가능 | 의미 기억에 포함 |
| 자기 기억 | 핵심 — 다음 학습 목표를 정하는 근거 | **구현** |

**층은 실제로 다르게 쓰일 때 나눈다.** 미리 6개로 나누면 6개를 동기화
하는 코드만 늘고, 각 층이 뭐가 다른지는 아무도 모르게 된다.

v0.1 = 사건 / 의미 / 자기 세 층. 나머지는 필요가 증명되면 분리한다.

특히 **자기 기억이 v0.1에 반드시 포함되어야 한다.** Existence Drive가
"어디를 배울지"를 고르려면 "내가 어디를 못하는지"를 알아야 하고,
그게 자기 기억이다. 이 둘은 같은 시스템의 양면이다.

---

## 6. 모순 탐지는 초기에 폭발한다

"모순은 실험 생성 장치"는 맞다. 그런데 경험이 적을 때는 **거의 모든
것이 모순처럼 보인다.** 조건 변수가 관측되지 않았을 뿐인데 모순으로
분류된다. 모순 큐가 수백 건으로 불어나고 아무것도 해소되지 않는다.

### 필요한 것 — 모순 우선순위

모순은 전부 같은 가치가 아니다. 정렬 기준은 Phase 1의 Drive와 같다:

> **이 모순을 해소하면 예측력이 얼마나 오르는가 / 해소 비용은 얼마인가**

- 자주 등장하는 상황에 대한 모순 > 한 번 본 상황
- 구분 실험이 싼 모순 > 비싼 모순
- 이미 다른 지식이 의존하고 있는 모순 > 고립된 모순

상위 N건만 활성 상태로 두고 나머지는 대기시킨다. **모순 큐에 상한이
없으면 호기심 엔진은 첫 주에 마비된다.**

---

## 7. 저장소는 3종을 쓰지 않아도 된다

제안: PostgreSQL + Vector DB + Graph DB.

v0.1에서는 **Supabase(Postgres) 하나로 전부 된다.**

- 구조화 데이터 → 일반 테이블
- 유사 경험 검색 → `pgvector`
- 경험 그래프 → `experience_edges(from_id, to_id, relation)` 인접
  테이블 + 재귀 CTE

세 개의 저장소는 세 개의 정합성 문제를 만든다. 그래프 쿼리가 실제로
Postgres에서 느려지는 것을 확인한 뒤에 Graph DB를 도입하는 게 맞다.
지금은 그 시점이 아니다.

---

## 8. Rookery에 이미 있는 것을 버리지 않는다

`src/lib/memory/`에 이미 상당 부분이 구현되어 있다:

- 카테고리별 저장, 신뢰도(low/medium/high), 유효기간
- 충돌 감지 (`knowledge_conflict`, `memory_conflict`,
  `source_conflict`, `time_sensitive_change`)
- 검증 상태 (`active` / `pending_review` / `archived` / `rejected`)
- 실행 시 회상 및 적용 (`retrieval.ts`, `context.ts`)

Phase 2가 제안하는 것과 **결정적으로 다른 점은 딱 하나**다:

> 기존 memory에는 **예측이 없다.**
> 결과를 보고 나서 교훈을 추출한다. 예측 → 결과 → 차이가 아니다.

그래서 Genesis v0.1의 첫 구현은 새 시스템을 빈 공간에 짓는 게 아니라
**실행 엔진에 예측 잠금 단계를 추가하는 것**이 되어야 한다:

```
현재 : 배정 → 실행 → 산출물 → (사후) 교훈 추출 → 기억
Genesis : 배정 → [예측 커밋] → 실행 → 산출물 → 매니저 판정
          → 예측 vs 실제 → 경험 저장 → 기억 수정
```

`src/lib/execution/engine.ts`가 이미 모든 공통 절차를 소유하고 있으므로
예측 커밋은 거기 한 곳에 들어간다. 스킬별 분기가 필요 없다.

이 방식의 이점이 큰 이유:

1. **행동할 수 있는 환경이 이미 있다** — 실제 업무, 실제 산출물
2. **AI가 조작할 수 없는 채점자가 이미 있다** — 매니저 승인/반려
3. **대사(비용 한도)가 이미 있다** — 회사당 $3/30일

Existence Drive가 요구하는 세 가지가 전부 이미 존재한다. 시뮬레이션
환경을 새로 만드는 것보다 훨씬 빠르고, 무엇보다 **Grounding이 진짜다.**

## 9. 성공 기준의 측정 프로토콜

Phase 2가 제시한 최종 기준은 옳다:

> 같은 문제를 두 번째 만났을 때, 첫 번째보다 명확하게 더 잘 해결하는가?

이걸 실제로 측정하려면 프로토콜이 필요하다. 그렇지 않으면 "좋아진 것
같다"로 끝난다.

```
1. 유형이 같고 내용이 다른 업무 쌍을 준비 (A1, A2)
2. A1 실행 → 예측·결과·매니저 판정 기록
3. 경험 저장 및 학습 반영
4. A2 실행 → 동일 기록
5. 비교 지표:
   - 예측 오차 감소폭
   - 매니저 수정 요청 횟수
   - 완료까지의 비용
   - A1에서 지적된 문제의 재발 여부  ← 가장 중요
```

마지막 항목이 핵심이다. **한 번 지적받은 문제가 다시 나오지 않는가.**
이게 되면 기억이 저장소가 아니라 성장 장치로 작동하는 것이고, 안
되면 앞의 지표가 아무리 좋아도 의미가 없다.
